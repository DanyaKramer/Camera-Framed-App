# Frame — камера с авто-кадрированием

iOS-приложение для съёмки фотографий с ручным режимом (диафрагма / выдержка / ISO),
настраиваемыми соотношениями сторон, сеткой по правилу третей и фишкой —
**автоматическим поиском удачного кадра и наведением камеры на него**.

Минимальная версия: **iOS 17**. Только iPhone. Всё считается на устройстве,
сеть не используется.

## Сборка

Сборка возможна только на macOS. Проект лежит в старом формате `pbxproj`
(`objectVersion = 56`) и открывается в **Xcode 14, 15, 16 и 26** — это сделано
намеренно, чтобы одинаково работать и на новых Mac, и на старых Intel.

| macOS | Максимальный Xcode | Проект откроется |
|---|---|---|
| Ventura 13.5+ | 15.2 | ✅ |
| Sonoma 14.5+ | 16.2 | ✅ |
| Sequoia 15.3+ | 16.4 | ✅ |
| Tahoe 26.2+ | 26.4 | ✅ |

```bash
open CameraApp.xcodeproj
```

Выбрать схему `CameraApp`, задать команду подписи (Signing & Capabilities → Team),
запустить на устройстве. Эмулятор не подойдёт — нужна реальная камера.

`Info.plist` генерируется автоматически (`GENERATE_INFOPLIST_FILE`), строки
использования камеры и фотоальбома берутся из `Resources/Info/UsageDescriptions.json`.

### Проект генерируется скриптом

Файл `project.pbxproj` **не редактируется руками**. После добавления или удаления
`.swift` файла запусти:

```powershell
powershell -ExecutionPolicy Bypass -File Tools/generate_project.ps1
```

Скрипт пересобирает проект из дерева исходников. Схема `CameraApp` — shared,
лежит в `CameraApp.xcodeproj/xcshareddata/xcschemes/`, поэтому `xcodebuild -scheme`
работает без ручных действий.

## Сборка без своего Mac: GitHub Actions

В репозитории лежит `.github/workflows/build.yml`. Он собирает проект на
macOS-раннере GitHub и показывает все ошибки компилятора. Это самый дешёвый способ
узнать, что код не компилируется, не имея Mac под рукой.

**Бесплатно**, если репозиторий публичный: стандартные macOS-раннеры для публичных
репозиториев не тарифицируются. Для приватного — macos-latest стоит $0.062/мин
(~$3.72 за час непрерывной сборки).

Запуск:

```bash
git init
git add .
git commit -m "Frame: camera app with auto framing"
git branch -M main
git remote add origin https://github.com/<твой-аккаунт>/<репозиторий>.git
git push -u origin main
```

После этого на странице репозитория во вкладке **Actions** будет видно, собралось
или нет. Артефакт `CameraApp-unsigned` содержит `.app` — его можно скачать и
положить в папку **Applications** на айфоне через Finder (подпись не пройдёт,
но хотя бы что-то увидишь; полноценная установка — только через Xcode).

### ТестFlight без Mac вообще

Если добавить в GitHub Secrets `APPLE_ISSUER_ID`, `APPLE_API_KEY_ID` и
`APPLE_API_PRIVATE_KEY` (это ключ .p8 из App Store Connect), в workflow появится
шаг загрузки сборки в TestFlight. Приложение придёт прямо на айфон через
приложение TestFlight.

Требуется платный Apple Developer Account — **$99/год**. Окупается, только если
приложение пойдёт дальше хобби.

Минус: TestFlight не даёт отладчика. Ни точек останова, ни логов, ни live-отладки
камеры. Для этого приложения, где вся суть в реакции на живой кадр, отладка на
реальном устройстве незаменима — так что CI полезен как «ловец ошибок
компиляции», но не как замена живому Xcode.

## Ключевые технические решения

### 1. Диафрагму на iOS задать нельзя

`AVCaptureDevice.lensAperture` — только для чтение, объектив физически фиксирован.
Поэтому выбор f-stop реализован как **экспозиционная компенсация**:

```
ΔEV = 2 · log2(N_выбранное / N_реальное)
```

При закрытии диафрагмы света становится меньше — экспозиция компенсируется вверх,
ровно как на реальной камере с объективом. Плюс опциональное размытие фона
по карте глубины (`DepthOfFieldRenderer`). В интерфейсе это помечено как
эмуляция.

### 2. Ручная экспозиция в момент съёмки

`device.setExposureModeCustom` влияет только на превью. Реальное фото снимается
через `AVCapturePhotoSettings`, поэтому точная пара `(duration, ISO)` дублируется
туда через `setCustomPhotoExposureMode`, а фактически использованные значения
читаются из `AVCaptureResolvedPhotoSettings`.

Поддерживаемые сочетания ограничены железом, и AVFoundation их не публикует.
`ExposureClamper` делает аналитический кламп (быстрый путь), а
`ExposureVerifier` проверяет пару вызовом и при отказе деградирует ISO/выдержку
по лестнице, запоминая удачный результат.

### 3. WYSIWYG: координаты превью и анализа — одно пространство

Коннекшены превью и `AVCaptureVideoDataOutput` получают одинаковый
`videoRotationAngle`. Превью использует `videoGravity = .resizeAspect`,
поэтому весь кадр виден и нормализованные координаты анализа напрямую
переносятся в экранные. Это же пространство используют маска аспекта и сетка.

Если бы `videoRotationAngle` не совпадал, стрелки наведения указывали бы мимо —
поэтому это первое, что нужно менять, если добавится фронтальная камера
с зеркалированием.

### 4. Зум центрирует кроп — отсюда решатель `FramingSolver`

`videoZoomFactor` всегда даёт **центрированный** кроп. Кадр, выбранный не по
центру (например, объект смещён к трети), зумом не воспроизвести.

`FramingSolver.solve` тратит весь доступный зум и остаток смещения переносит в
пост-крос:

1. зум, при котором кроп ровно заполняет кадр: `z' = z / cropWidth`;
2. зум, при котором кроп ещё помещается в центрированную область с учётом
   смещения: `z ≤ 1 / (cropSize + 2·offset)`;
3. берётся меньший, кроп проецируется в координаты доставленного снимка.

Так превью, сетка и итоговое фото совпадают до пикселя.

### 5. Как ищется «красивый кадр»

Слой 1 — **что важно** (`SubjectDetector`): лица → человек → salient-объект →
карта внимания → локальный контраст. Всё на Vision, офлайн.

Слой 2 — **как разместить** (`CropSearcher`): карты стоимости (салиенси, маска
субъекта, яркость, пересветы, плотность границ) на кадре ~192 px; на каждую
натягивается `IntegralImage`, после чего оценка любого кропа — четыре обращения
в память. Поиск: грубая сетка по масштабу, затем координатный спуск.

Скоринг (`CropScorer`) — взвешенная сумма «бугров» 0…1: заметность, заполнение
кадра, попадание в power-точки третей, воздух над головой, опережающее
пространство, запас по краям, уровень горизонта, качество экспозиции, визуальный
шум по периметру. Все веса — в одном файле `CropScoreWeights`: вкус в кадрировании
это продуктовое решение, а не техническое.

Экспозиция замеряется отдельно (`Metering`) гистограммой **внутри найденного
кропа**, с откатом вместо пересветов и ограничением усиления в тёмных сценах.

### 6. Производительность

- `alwaysDiscardsLateVideoFrames` + слот «только последний кадр» (`FrameStreamer`)
  — анализ не копит очередь.
- Полный скан: анализ 192 px, сегментация человека включена. ~0.5–1.2 с.
- Живое наведение: анализ 128 px, сегментация выключена, ~9 Гц.
- `IntegralImage` строятся один раз на кадр; поиск кропа — единицы миллисекунд.

## Язык интерфейса

Цвет здесь несёт смысл, а не украшает:

| Цвет | Состояние | Что значит |
|---|---|---|
| `accent` (жёлтый) | приложение предлагает | кнопка скана, активный пил зума |
| `live` (янтарный) | нужно подвинуть камеру | бокс субъекта, крестик, строка-команда |
| `success` (зелёный) | кадр совпал | можно снимать |
| `white 45%` | покой | подсказка «нажмите, чтобы найти кадр» |

Правило наведения: **одна команда за раз**. Показывать «сместите вниз», «приблизьте»
и «добавьте света» одновременно бесполезно — пользователь не знает, с чего начать.
`LiveMatcher.primaryInstruction` выбирает самое сильное отклонение, измеренное в
собственных допусках своей оси.

Состояния кнопки скана: `✦` — сканировать, `↻` — пересканировать (рецепт сохранён,
наведение выключено), `✕` — выйти из наведения.

Оверлей наведения рисует **пунктирный бокс вокруг найденного субъекта** с выноской
в центр кадра. Один крестик говорит «двигайся», бокс говорит «двигай *это*».

### Чего сознательно нет

- **Подписи типа «чёрные кожаные ботинки»** — из макета. Текущий `SubjectInfo.Kind`
  даёт только «лицо / человек / объект». Полноценная подпись требует
  `VNClassifyImageRequest` на кропе bbox субъекта плюс фильтрацию физических
  классов из ~1300 и словарь локализации.
- **Ручной режим на макетах не показан** — он есть в приложении, но в визуальном
  прототипе его не было. Фейдеры вынесены в отдельный слой над строкой-командой.

## Что не сделано / известные ограничения

- **Не проверено на устройстве.** Код написан и вычитан, но ни разу не компилировался
  и не запускался — в среде разработки нет macOS. Ожидайте правок компилятора.
- Фронтальная камера не переключается: граф настраивается только на заднюю.
- `DepthOfFieldRenderer` использует `AVDepthData` из захвата. Там, где карты глубины
  нет, работает центральный радиальный фолбэк — он не является настоящим боке.
- Тема гистограммы замеряет весь кадр, а не только область съёмки.
- `photoQualityPrioritization = .quality` может переопределить запрошенные ISO/выдержку
  — фактические значения читаются из `AVCaptureResolvedPhotoSettings`, но интерфейс
  показывает запрошенные. Стоит показывать и фактические.
- RAW: если включён, `fileDataRepresentation()` отдаёт DNG, и в альбом попадает
  именно он — JPEG-версия не сохраняется. Нужно развести запрос и сохранение.
- Тёмные сцены: замер не различает «мало света» и «тёмный объект».
- Нет юнит-тестов. Первый кандидат на них — `IntegralImage`, `FramingSolver`
  и `CropScorer`: чистые функции с заранее известным ответом.
- Тёмные сцены: замер не различает «мало света» и «тёмный объект».
